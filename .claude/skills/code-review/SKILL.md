# Code review — independent adversarial pass

## When this fires

After every applicable `verify-*` skill has passed for a unit — `verify-tests` always, `verify-evals`/`verify-ui`/`verify-rls` as applicable — and **after that unit has been committed locally.** The commit is what gets reviewed, so it has to exist first; the gate this skill holds is the push, not the commit. Nothing unreviewed reaches the remote, and a local commit nobody has pushed is not published work. Running this before those pass would waste an independent, adversarial pass on code that isn't even behaviorally correct yet; fix what the cheap mechanical checks already catch first, then spend this on what they structurally can't.

Skip only when `scope` itself was skipped for this task (a genuinely trivial single-line fix or pure copy/text change with no logic impact) — the same bar `scope` uses, since a change too small to need a blueprint is also too small to need an independent adversarial pass. A task that got a scope entry but no full scope doc (`scope`'s middle tier) still goes through this gate — "simple enough to skip the doc" is not the same claim as "simple enough to skip an independent check."

## Procedure

1. **Assemble what the reviewer gets — deliberately not what the builder has. One package per unit of work, not one per task.** For each unit, its own commit's diff (`git show <sha>`) and the one-sentence deliverable of that unit, taken from the `- [ ] **U<n>** —` line in the task's `## Done when`. **The commit says which unit it is** in a `Unit: U2` line next to `Task:`, and the unit's `- commit:` line in `## Done when` names its SHA once it is integrated or recorded; the subject is not read. A task whose commits carry no `Unit:` line gets reviewed by whatever grouping its history actually has, and the log says that is what happened. Where the task ships as a single unit, that is the whole of it and the package says so. A task's scope doc or PRD in `/docs` is context you may point the reviewer at; it is not the stated intent, because the intent being checked is the unit's. Do not hand over this session's own chat history, reasoning, or assumptions along with it — that shared context is exactly what would defeat the independence this skill exists for. The reviewer forms its own understanding of the code from the code, then checks that against the stated intent — it doesn't inherit the builder's read of its own work.
2. **Review commit by commit, not as one squashed diff.** The task's `## Done when` lists its units of work, one per commit; each commit gets its own reviewer pass, with that unit's stated deliverable as the intent it is checked against. A single pass over the combined diff is a weaker check: it sees the end state, so a defect introduced in one commit and papered over in a later one reads as correct, and the reviewer never has the unit's own intent to compare against.

   **The only thing that collapses into one pass is work that genuinely landed as one commit**, and the log says so rather than letting it look like two passes happened.

   **The closing commit is not a unit.** Setting the task to `done` and regenerating the indexes lands as its own commit, which carries no deliverable and gets no pass of its own.

   **Then one final pass over the combined diff, scoped to interactions only** — an inconsistency between the third unit and the seventh is precisely what no single-commit pass can see. It does not repeat what the per-unit passes already did, and it is skipped for a task of one unit.

3. **Dispatch one `code-reviewer` subagent per package** (defined at `.claude/agents/code-reviewer.md`), each a fresh instance with no continuation of this session's context and none of another reviewer's. A task of four units dispatches four, plus a fifth for the final interaction pass — which is its own dispatch, carrying the combined diff and the instruction to report only what crosses unit boundaries. Independent units can be dispatched at once; a unit that depends on another is dispatched after that one's findings are resolved, because reviewing against a base that is about to change wastes the pass. If the current environment can't actually invoke a distinct subagent definition, fall back to reading `.claude/agents/code-reviewer.md` yourself and following its charter procedurally — but say so explicitly in the `review-round` entry of step 5. A same-session fallback is a materially weaker check than a real independent pass, and the project owner should know which one actually happened, not have it look identical either way.
4. **Triage the returned findings:**
   - Any **BLOCKING** finding stops the task here. Fix the underlying issue, re-run whichever `verify-*` skill(s) cover the area touched by the fix to confirm nothing that was passing broke, then dispatch a **fresh** `code-reviewer` instance against the updated diff — **amend the unit's own commit while it is unpushed and still the last one on the stack**, so that one unit stays one commit however many rounds it takes; once later units sit on top of it, amending would mean rewriting every commit above, so the fix lands as its own fix commit carrying the `Unit:` line of the unit it corrects (one fix commit per unit) and gets its own review round citing its sha; the unit's `- commit:` stays its original commit; once pushed, neither applies and the fix goes forward in a new commit — never ask the same reviewer instance that raised the finding to bless your own fix; a new instance re-reads the whole diff without anchoring on its own prior verdict. The only other way past a BLOCKING finding is the project owner explicitly accepting the risk in writing — never downgrade or dismiss one yourself, whether you're the builder or standing in for the reviewer.
   - **At most two review rounds per unit, then the project owner decides** (T147, T026). A round with no BLOCKING finding closes the unit: record its FLAGs and move on, and never reopen the unit to fix flags, because an amend restarts the cycle. A flag worth fixing becomes its own small unit, reviewed once. Set the blocking bar in the reviewer prompt up front: the BLOCKING definition under "Severity" in `.claude/agents/code-reviewer.md`, calibrated to the project's `maturity:`. If the unit already has two rounds or more and the last one left a BLOCKING finding, `scripts/task-log-append.mjs` refuses to record another, and the session dispatches no further reviewer: it takes the unit to the project owner as a class A decision — accept the risk in writing, re-scope the unit, or open one more round. The owner decides; the session records that decision with `scripts/task-log-append.mjs … decision --by <owner> --unit U<n>`, saying where the owner took it (the chat, a control-center card), and never writes one the owner did not take. One such entry opens exactly one round. A re-scoped unit takes a new number, never one already used in the task. The decision may also produce new work: a new unit in the same task, or a new backlog task carrying notes on its risk and priority. What counts as a round, and when a later review passes without a decision, is in "At most two review rounds per unit" in `ae-kit-templates/task-log-ontology.md`.
   - **FLAG** findings don't block `ship`. Record them anyway — this skill's job is that the project owner is never blindsided, not that every finding stops the world.
5. **Record the outcome in the task's task log (`logs/tasks/<id>.md`)**, with `scripts/task-log-append.mjs` — see "How the skills write" in `ae-kit-templates/task-log-ontology.md`. This session writes it — never a reviewer, and never any agent dispatched to work on a unit while anyone else works on the same task: that agent returns its rounds and findings in its reply, and the session that dispatched it appends them ("One writer per task log" in the ontology). **Each unit's `review-round` is written with `--unit U<n> --commit <sha> --blocking <count>`** — the unit, the sha of the commit the reviewer read, and how many blocking findings it left — because `integrate-unit.mjs` reads those three fields and nothing else: not the body, not `result:`. A round of no single unit — the final interaction pass, or "U1 and U2 as one commit" — carries none of the three and says what it covered in its first sentence, because a log that says "4 rounds" over six units cannot tell a reader which two went unreviewed. A unit deliberately left unreviewed, or a final pass skipped because the task had one unit, is a sentence in the log, not an absence.

   **Write each round with its own findings immediately behind it, before opening the next round.** The generated view has no field tying a finding to a round: it attributes each one to the last `review-round` written above it. Dispatching several units at once and then writing all the rounds followed by all the findings puts every finding under the last unit — a log that names the wrong unit is worse than one that names none, because it reads as precise. The reviewer's report is not copied in:

   - **One `review-round` per review**, with `by:`, `result:`, and `ref:` pointing at the report the subagent collector saved under `logs/subagents/<YYYY-MM-DD>/` — and, for a unit's round, `unit:`, `commit:` and `blocking:`.

     **Find that folder by the reviewer's agent id — the one the dispatch returned — and by nothing else.** The folder name ends in the **first 12 characters** of that id — the collector truncates it (`subagent-collector.mjs`, `shortId`) — so `ls -d logs/subagents/*/*"${id:0:12}"` finds it in one command, across every day, without knowing which one it landed in. Searching for the whole id matches nothing, silently, and the folder then looks absent when it is sitting right there. If the dispatch returned no id at all, the collector takes those same 12 characters from the transcript filename (`agent-<id>.jsonl`), and only hashes the path when even that does not match — so try the 12-character match first anyway, and fall back to the type and description, saying in the entry that the id was not available. Two folders matching is not a case the collector produces (it reuses one folder per id); if it ever happens, link the one whose `input.md` names this task. Never pick it by time ("the most recent folder") and never by description: the timestamp in the name is when the collector first wrote the folder, not when this reviewer finished, and two reviewers dispatched for the same task on the same day share the type and very nearly the description — the id is the only part of the name that tells them apart. It is also why a second round is a second `review-round` entry with its own `ref:`: linking one reviewer's report never links the other's.

     **One folder can hold more than one reply.** A reviewer that stopped and then resumed is saved again beside what was already there — `output-2.md`, `output-3.md` — because nothing already saved is ever rewritten. In that case `output.md` is the partial one: link the **highest-numbered** `output` file in the folder, which is the complete reply. Open it before linking it; a report that stops mid-sentence is a partial one whatever its number, and a `ref:` to it points the owner at half a review.

     **No folder at all is a legitimate outcome, and it is written down as one.** If the project never got the collector's `SubagentStop` hook declared (that is what `R36` verifies), or the collector ran and saved nothing, there is no path to point at: say exactly that in the entry, and give each finding below its full text instead of a pointer. Never write a `ref:` to a path you have not seen on disk — a link that resolves to nothing reads as evidence and is worse than a stated absence.
   - **One `finding` per finding**, with its `severity:` — its trigger and its consequence, close to the reviewer's own wording.
   - **One `fix` per finding fixed**, with `resolves:` naming the finding's entry and `--commit <sha>` naming the commit the fix landed in. For a `BLOCKING` finding the commit is the unit's own and is optional. For a `FLAG` of this task log that came out of a unit's round it is required — not for a flag of a round without `unit:` or written before any round, nor for a `resolves:` into another task's log: a flag is fixed in a new unit, never inside the one it came from, so its `fix` is written only after the review round of the new unit — the appender refuses the fix of a flag whose commit no round of another unit reviewed after the flag, or that a round of the flag's own unit reviewed. **The exception:** when the flag's round left BLOCKING findings the unit is amended anyway, and a flag may be fixed in that same amendment — recorded with `destination: fix`, and its `fix` citing the commit the next round of that unit reviewed. Only flags that pass the questions in "Which flags get fixed now" of `ae-kit-templates/severity-rubric.md` go into it, and each one counts toward the two flag fixes per task; both are this session's judgement, which no script counts yet ("A flag is fixed in a new unit" in `ae-kit-templates/task-log-ontology.md`). A `BLOCKING` finding the project owner risk-accepted gets a `decision` entry with `by:` and `resolves:` instead — their explicit, dated confirmation, linked to the finding it applies to.

   **The task file receives only the `BLOCKING` findings still open**, under its `## Open blockers`, one line each with the id of its entry, and loses that line when the finding is resolved. Everything else is in the task log.
6. **Hand off to `ship`** once there are zero open `BLOCKING` findings across every unit — **counted in the task log**: a `finding` with `severity: blocking` that no `fix` or `decision` resolves. The task log decides; `## Open blockers` is a pointer to it, and if the two disagree, fix the task file to match (each one fixed-and-reverified, or explicitly risk-accepted).

## Output

A recorded independent review in the task's task log — either a genuine "nothing found" after a real adversarial attempt, or its findings with every `BLOCKING` one resolved (fixed-and-reverified, or explicitly risk-accepted by the project owner) and every `FLAG` one left visible — before `ship` runs.

```yaml
output:
  - kind: task-log
    event: review-round
    must_contain: who reviewed, the result, and a ref to the saved report — or a statement that none was saved
  - kind: task-log
    event: finding
    must_contain: one entry per finding, with severity, trigger and consequence
  - kind: task-log
    event: fix
    must_contain: one entry per finding fixed, resolving it — or a decision entry where the owner risk-accepted it
  - kind: task-entry
    must_contain: only the BLOCKING findings still open, each with the id of its entry
```
