# Build

## When this fires
Immediately after `scope` (and `design` and `adversarial`, if they ran) for the approved task. Branch according to this project's policy (`CLAUDE.md` → Git conventions); the kit default is a branch only while another writer is active at the same time.

**If `adversarial` ran, its approved case list is an input to this step, not a document to acknowledge.** Every case on it either gets a test here or gets flagged back — a case that was approved and then quietly dropped leaves a record claiming coverage that doesn't exist, which is worse than never having listed it.

## Procedure

1. **Set the task to `in progress` and regenerate the indexes, before the first unit.** `scope` leaves a task at `todo` when its plan was written for a later day, and this is the skill where work actually starts. A task built, committed and reviewed while still reading `todo` never appears in `TASKS.md`, so `open-session` cannot recommend resuming it and its stall check never fires on it — an interrupted build goes invisible at the next session open.

   **That edit and the regenerated indexes are staged with the first unit's commit**, and `commit` step 2 names them as the one addition its "nothing else" allows. Left out, they sit uncommitted for the whole task, which is the index drift `R3` and `R20` exist to catch and which the pre-commit index check raises again on every later unit commit. When `scope` started the work the same day, the edit already happened there (`scope` step 8, before any unit existed) and this step has nothing to set — the task's state still travels in the first unit's commit exactly the same way.

   **Work one unit at a time, in the order their `depends on` fields allow.** The task's `## Done when` lists its units, and each one is a separate trip through this skill and the next three: build it, hand it to `verify-tests`, commit it locally with `commit`, and let `code-review` pass over that commit. Then start the next. Building all of them and verifying once at the end is the shape this rule exists to replace — it produces a single diff nobody can review in pieces.

   Units that depend on nothing can be built in any order. A unit whose `depends on` names another waits for that one to land.

   **Whether units go to other agents is the project's branch policy, not this skill's call** (`CLAUDE.md` → Git conventions). With a single writer, nothing below dispatches anything: units are built one after the other in the checkout, as always. It still runs `--plan` (below) before each unit, because a file another task has is not its to write either. It also records each unit with `integrate-unit.mjs record`, which checks the unit's files against other tasks by the same rule as `check` (D052). When `record` refuses, the commit is already on the tracked branch, and what to do is the project owner's to say. The dispatch paragraphs apply when the policy delegates. What `--plan`'s exit means, in both modes:

   - **0** — build or dispatch the units it lists as ready. A unit it lists as `Waiting` is neither built nor dispatched yet, and the report to the owner or the task log says which one waits and on whom, so it does not stall in silence.
   - **1** — the task or the call is wrong: read what it prints, fix it, and run it again before building.
   - **2** — it could not check: the task could not be read, or what other tasks have could not be (no repository, a base that is not a commit, a main checkout on a detached HEAD, an `ai/` or `proto/` branch or mid-rebase, another task in flight whose units cannot be read). Nothing is dispatched or built until what it names is resolved and it runs again. A 2 never means "go ahead".
   - **3** — some unit has no `touches:`, or the task predates units. A 3 is a stop for the unit without `touches:`, not a notice, in either mode: that unit is not built or dispatched until it has them (as below). The task's other units go on as on a 0 — `--plan` still lists them as ready — and the 3 the missing one keeps causing does not hold them. A task that predates units has no unit to go on with, so nothing of it is built.

   A project with no git — `git rev-parse --show-toplevel` fails at its root: no `.git` there or above — exits 2 on every `--plan`. It cannot delegate, and no other task can have a file in it: its single writer runs `task-units.mjs <task>` without `--plan`, skips `record`, and builds. Without `--plan` the script prints no order and does not check that the units a `depends on:` names exist: it only checks that each pending unit's `touches:` is valid and its `depends on:` present, so the writer takes the order from the `depends on:` lines themselves, as above. Otherwise the exits mean what they mean with `--plan`: on a 3 the unit without `touches:` is not built, and the others go on, as in the bullet above; on a 1 it fixes what it prints, and it runs `task-units.mjs <task>` again before building the unit it fixed.

   **Which units go out together is computed, not judged.** Run `scripts/task-units.mjs <task> --plan`, with `--in-flight` naming the units already out (in the repo that produces the kit, the copy to run is `kit/scripts/`). It lists the pending units that are ready: no dependency still pending, no file in common with each other or with a unit in flight, and no file another task has. Who has what is read from git, and listed under "Other tasks": a unit of another task dispatched and not integrated (a live worktree, or a branch with a commit), or the branch `ai/<task>` of any task not `done` or `dropped`, noted when that task is not `waiting on owner` (the rule is in the header of `task-units.mjs`). A unit with such a file is listed as `Waiting`, naming the task and unit that has it, and is not dispatched: the first unit dispatched wins. It is released when that unit integrates, or, for a branch `ai/<task>`, when that branch integrates or its task reaches `done` or `dropped`; `integrate-unit.mjs integrate` and `discard` both print which units of other tasks no longer wait, and `--plan`, run again, is what dispatches them. When the policy delegates, dispatch the ready units, each to its own agent in its own worktree, and nothing else.

   **Create a unit's worktree before planning the next task or dispatching another unit.** A unit has its files only once its worktree exists, or its branch has a commit: until then, `--plan` on another task sees them free, and one session can send two units of two tasks to the same file in the same turn.

   **A unit with no `touches:` is not built or dispatched** — the script exits 3 and names the units missing it. The session does not fill the field: it sends the unit back to `scope`, which settles how the work splits into files with its reviewer (class B, `ae-kit-templates/decision-classes.md`), and `scope` writes its `touches:` (splitting it again if it has to). This holds by a single writer or delegated. The task's other units go on meanwhile, as on a 0. A guessed list would let two units collide unseen, and building the unit anyway for `check` or `record` to catch a collision afterwards is detecting and redoing, the model the project owner reverted (D027). A task that predates units altogether (no `**U<n>**` lines) goes back to `scope` the same way, which writes its units with their `touches:` before anything of it is built.

   Implement the unit described in the blueprint, writing only the files its `touches:` declares. The task's state files (`tasks/`, `logs/tasks/`, `TASKS.md`, `BACKLOG.md`, `TASKS_ARCHIVE.md`) are never declared in `touches:` and never count as undeclared: only the session writes them, and `integrate-unit.mjs check` rejects them in a unit's commit. **A builder that needs any other file does not write it until it has an answer.** A dispatched builder cannot ask and wait mid-run, so it commits what it has, stops, and returns the question. Committing first is what keeps the unit whole if it has to wait and be rebased; the rest of its work amends that commit, so it still returns as one. The session that dispatched it answers by whose the file is. "Goes on" below means the session dispatches the builder again, or resumes it, in the same worktree with the answer:

   | The file belongs to | What the session does |
   |---|---|
   | No unit of this task, and another task has it (`--plan` lists it under "Other tasks") | The asking unit waits, reported as a `Waiting` unit is: it does not write the file until it is released (as above), then goes on as in the next row. Only between two units, when both declared the file or neither did, does the project owner decide which one waits (D049) |
   | No unit of this task, and nobody has it | Adds it to the unit's `touches:` and to the blueprint's file impact list, with a task-log note. Class B: the builder goes on without waiting. When another task changed the file on the tracked branch after the unit started, the unit's branch is first rebased onto the tip with `integrate-unit.mjs rebase`, before the builder edits it: otherwise `check` is certain to refuse the unit |
   | A unit already integrated | The same, and the unit's branch is first rebased onto the tip with `integrate-unit.mjs rebase`, so it builds on that unit's version |
   | A unit of this task not started yet | Adds it to the asking unit's `touches:`, with a note. The builder goes on; the other unit will be built on this version, and nobody waits for a unit that has not started |
   | A unit of this task still in flight | The asking unit waits for that unit to be integrated, then goes on as in the row of a unit already integrated |

   **A waiting unit's `touches:` is not widened while it waits**: `integrate-unit.mjs check` would count it as in flight on that file and refuse the unit that has it. It is not dispatched again and does not write the file; it is widened, and its branch rebased with `integrate-unit.mjs rebase`, once that unit is integrated. Two units of this task waiting for the same file take it one at a time, in the order they asked; two that each wait for a file of the other go to the project owner.

   **When `check` refuses a unit over a file, the instruction depends on why**, and `integrate-unit.mjs` prints it with the refusal:
   - **`held`** — another task has the file: a unit of it, or its branch `ai/<task>`. Nobody is asked and the unit is not rebuilt yet: it waits, reported, until the file is released (as above), then goes through `integrate-unit.mjs rebase`, which checks again and says whether it must be rebuilt (it must when the other unit changed the file, which is the usual case).
   - **`held-both-declared`, `held-both-undeclared`** — the file is had by a unit of another task, and both units declared it, or neither did, so `check` does not choose: the project owner decides which one waits (D049). Until then nothing is integrated, discarded or rebuilt.
   - **`overlap`** — the file changed on the tracked branch after the unit started, or another unit of this task in flight has it. The session discards the branch and rebuilds the unit from the current base; it never repairs the branch or merges over the other edit. That holds unless the same run also brings a `held` or `held-both-*`: then it waits as that refusal says, and so do `merge-commit` and `main-checkout-write`.

   A unit whose builder is gone keeps its files with no deadline; the wait names it, and `integrate-unit.mjs discard` releases it. Discarding another task's unit is the project owner's call: class A in `ae-kit-templates/decision-classes.md`, since it deletes work outside this task's approved scope. **A unit's branch is rebased only with `integrate-unit.mjs rebase`, never with a plain `git rebase` in its worktree**: a rebase by hand moves the unit's starting point past the other edit, so `check` no longer sees that the file changed under it, and it can hide that another task has the file too. A unit that `rebase` refuses for an overlap is rebuilt, not rebased by hand.

   Whoever the file belongs to, a request that changes what gets built, not just which files carry it, is a change of scope: class A in `ae-kit-templates/decision-classes.md`, and it goes to the project owner. **A class A question stops only the unit that raised it**: its worktree stays as it is, with the work it committed before asking, and the other units go on. A unit is rebuilt when `check` refuses it for an overlap. If the rebuild is refused for an overlap again, the third build runs alone, with no other unit in flight.

   **With a single writer, a file outside the list is class B too** — the project owner's decision of 2026-09-29, not an assumption: it is added with a note and the work goes on. It waits only when another task has that file (the table's first row), and it reaches the owner only if it changes what gets built. It is never written silently, and never on the `--plan` run from before the unit started: the writer runs `--plan` again before writing it.

   **A unit that turns out to be two gets split here, not worked around.** Rewrite the `## Done when` with both, each with its own verification **and its own `depends on`**, and say so in the task log. **The new unit takes the next free number and goes at the end of the list**, never renumbering the ones already committed — `commit` names each unit's commit in its `Unit: U<n>` line, `integrate-unit.mjs` records that commit under the unit as `- commit: <sha>`, and `code-review` maps a commit to a unit by those and nothing else. **The split is committed — the task file with both units — before either is built or dispatched:** the commit-msg hook checks a `Unit:` line against the task file staged in that commit, and a dispatched builder never writes `tasks/`, so a unit that exists only on disk refuses its own commit. Discovering it while building is normal; finishing it as one commit and noting the debt is what leaves the reviewer a commit with two intentions in it.
2. **Write tests/evals as part of this step, not after.** Deterministic tests for anything with a defined expected output (including integration tests for any API/service endpoint's auth, status codes, and error handling). If the feature involves a model call with non-deterministic output, flag it explicitly for `verify-evals` rather than trying to write a unit test against a variable output.

   **Two rules for anything that writes data, both learned from real bugs:**

   - **No write is assembled inside a component.** The decision about *which rows get written* is a pure function with its own tests — never logic living in JSX.
   - **Assert on the write's effect, not on the absence of an error.** An `UPDATE` filtered out by row-level security returns success having changed zero rows; a client that only checks for an error object reports a save that never happened. Read back what changed, or assert on the affected count.
3. Enforce the strict-mode compliance of the language named in `CLAUDE.md` → Stack as you go — this is not a separate lint pass at the end, it's a constraint on every line written.
4. Record the work in the task's task log (`logs/tasks/<id>.md`), with `scripts/task-log-append.mjs` — see "How the skills write" in `ae-kit-templates/task-log-ontology.md`: a `note` for what changed and how, in plain English, not file-by-file. The task file itself only changes where its state does — a unit checked off, an open blocker added or removed.

   **Write the unit's note before its commit, not after several units are built.** `commit` stages the task's task log whole, so a note written early travels in whatever commit comes next: write three notes and then make three commits, and the first commit carries all three — including a claim about work that does not exist in it yet. Build, note, commit, next.

   **Commit the finished unit before handing the next one to another agent.** This is what keeps "one unit, one commit" true once more than one writer is involved. Two uncommitted pieces of work in the same file stop being separable: whoever writes second cannot tell which lines were already there, and splitting them afterwards means surgery on the hunks of a diff. The same holds for yourself when you pause one unit and start another. It is also the condition behind the parallel builds step 1 allows: two agents are safe at the same time only when their units share no files. The task's task log does not count as shared, because **any agent dispatched to work on a unit while anyone else works on the same task does not write to it** — a single background agent included: it returns its note in its reply, and the session that dispatched the agents appends every note, with `task-log-append.mjs`, once they have all finished — the same way `code-review` records what its reviewers return. The same holds for `verify-tests` and `code-review` run by that agent: see "One writer per task log" in `ae-kit-templates/task-log-ontology.md`. Those entries travel in the next commit the dispatching session lands — the next unit's, or the closing commit `ship` lands, which carries the task's state. One writer, appending in sequence, is what keeps the task log whole; the `merge=union` rule in `.gitattributes` (`commit` step 2) is only the net for when two branches touch it anyway, and it can drop lines (see the ontology). The price, accepted: a note the agent leaves out of its reply is a note nobody writes. When the units share any other file, run them one after the other. Their `touches:` fields are where you check whether they cross, and `task-units.mjs --plan` does the check.
5. When the **unit** is implemented, hand off to `verify-tests` — and to `verify-evals` and/or `verify-ui` if that unit involves an AI-native feature or a UI surface. "Complete" here means the unit, not the task: a task is done when its last unit has been through the whole chain, not when everything has been written and nothing verified.

   **When the policy delegates, the unit's worktree is also where its suites run one last time, before it is integrated.** `integrate-unit.mjs integrate` requires `--verify <command>`: it runs the command in that worktree, rebased onto the current tip, and the tracked branch moves only if it comes out green — red, nothing moved and nothing needs taking out. So the worktree stays until the unit is integrated, and it holds what the suites need: a file git ignores (a `.env`, `node_modules`) that exists only in the main checkout is not there, and a suite that needs it comes out red — **unless the test skips itself when its variable is missing**, and then it comes out green having tested nothing. `integrate` prints the command's output only when it comes out red, so a green run says nothing about skips: when the project's suites can skip themselves, run the suite command once in the unit's worktree before integrating, read which tests skipped, and say so in the task log — a skipped test verified nothing.

   **The command passed to `--verify` is the project's suite command, from `CLAUDE.md` → Stack, and never one chosen in the session.** The script accepts any command — `--verify true` integrates having run nothing — so this sentence is the only thing that stops it. That command starts from a clean install and build in a project with dependencies, because the worktree keeps the ignored files of earlier runs (a `node_modules`, a `dist/`) and a suite can pass on what the commit no longer produces. If `CLAUDE.md` declares no suite command, or it reads `TBD — deferred`, a delegated unit is not integrated: build the units with a single writer in the main checkout until it has one, and tell the owner that declaring it is a setup event (`setup/SKILL.md`). A project installed before this line existed has none: add it from what its CI or R4 already runs, and confirm it with the owner. There is no undo: a unit already integrated comes out with a plain `git revert` of its commit, and whoever reverts it unchecks it and removes its `commit:` line.

## Output
One unit implemented, its tests/evals written alongside it, and a task-log entry describing what was built in plain English — written before that unit's commit.

```yaml
output:
  - kind: task-log
    event: note
    must_contain: what was built, in plain English, organized by what a reviewer would check
  - kind: file
    path: the test files written alongside the implementation
    must_contain: for any task that writes data, at least one assertion on the write's effect
```
