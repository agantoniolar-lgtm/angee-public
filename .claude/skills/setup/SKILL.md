# Setup

## When this fires
- **Greenfield:** a new project is being started and needs the full framework from day one.
- **Retrofit:** an existing, already-running project has none of these guardrails yet and needs them added without disrupting existing code.

Both cases use the same skill; only step 2 differs.

## Before this skill can even be read: getting the kit files into the project

This skill only exists in a project because the kit was installed there first. **There is one path, and it goes to the remote:**

```bash
gh api repos/agantoniolar-lgtm/angee-public/contents/install.sh \
  -H "Accept: application/vnd.github.raw" | bash -s -- /absolute/path/to/project
```

It accepts `--ref <tag|branch>` for a specific version and `--dry-run` to see what would change without writing anything. **It overwrites the kit's files.** A file under `.claude/skills/`, `.claude/agents/`, `ae-kit-templates/` or `scripts/` that the kit ships belongs to the kit: one that differs from the new version is replaced, with no question asked. The report lists what it replaced, and apart the files the project had edited — they differed from the previous `.ae-kit-manifest`, or, without one, from the published version `.ae-kit-version` names — each with the git command that brings its previous content back. A file the kit no longer ships is removed if it is unchanged since it was installed, and left, reported once, if the project changed it. **In a git repository, it refuses, writing nothing (exit 4), when it cannot be sure git could bring back what it replaces** — usually because a kit file it would change has uncommitted changes, which you commit or stash before running it again. Its message names the cause to fix. **Outside a git repository it does not refuse**: it overwrites, exits 0, and reports that what it replaced cannot be recovered. In a project without git, run `git init` and commit first. **Before writing anything, it prints the release notes of every kit version between the installed one and the new one, and stops, writing nothing (exit 5), if any of them asks for steps "Before installing"** (see below). A fix the project needs in a kit file never lives in the kit file: it is a row of `CLAUDE.md` → Local kit adjustments (step 0a).

The installer always clones the remote, never a local checkout. **An unpushed change reaches no project at all.**

**Before installing, check whether the project already has a `.claude/`.** The installer writes only the paths the kit ships, but at those paths it overwrites whatever is there.

**If the project has no `.claude/` yet:** the installer writes everything cleanly, with nothing to replace.

**If the target project already has a `.claude/` folder** (settings, hooks, other project-level config, or its own skills): do NOT replace the folder. Only bring in `kit/.claude/skills/*` — each individual skill folder (`setup/`, `prototype/`, `scope/`, `design/`, `adversarial/`, `build/`, `verify-tests/`, `verify-evals/`, `verify-ui/`, `verify-rls/`, `commit/`, `code-review/`, `ship/`, `session-log/`, `open-session/`) — into the existing `<project>/.claude/skills/` (creating that subfolder if it doesn't exist yet). Everything else already under `.claude/` — `hooks/`, `commands/`, any unrelated existing skills — stays untouched. **`settings.json` is the one exception, and it is a single write:** the installer declares there the `SubagentStop` hook that runs `scripts/collect-subagent.mjs`, creating the file if the project has none and adding only that event if the file exists without one. It never reorders or reformats what is already in it, never replaces it the way it replaces the kit's *own* files (`settings.json` is not one), and never reads or writes `settings.local.json` — that file is not versioned, so a hook declared there runs for one machine and for nobody else. When it cannot make that write, the installer changes nothing, prints the exact block to paste, and **ends the install incomplete on purpose**. It cannot make it whenever the project already declares its own `SubagentStop`, the file does not parse as JSON or cannot be read, its top level is not an object, `hooks` or the event has an unexpected shape, the machine has no `node`, or the file's formatting is one that writing it back would not reproduce byte for byte — that last one refuses the write even when no hook of the project's is at stake, because rewriting someone's file in a formatting they did not choose is the promise this installer does not break. In every one of those cases the reason is: a project running the kit without that hook keeps no record of what its subagents were asked or answered, which is half the kit reporting itself green. **Check for overlap before installing — both by name and by purpose.** A name collision (the project already has its own `scope/`, `commit/` or `ship/` for something unrelated) is the easy case, and it is settled before the install, never after: **move the project's own skill off the kit's path** (e.g. to `.claude/skills/<project>-commit/`, with its own `name:`) and commit that. The installer writes the kit's skill at its path no matter what is there, and every later install writes it back and lists it as edited, so renaming the kit's copy instead only leaves an orphan the next install ignores. The harder, easy-to-miss case is *purpose* overlap under a different name — read every existing skill's full `SKILL.md` body, not just its frontmatter name and description, and compare its actual procedure against what each of the 15 incoming kit skills does. A project's own hand-built session-closing skill can cover exactly the same ground as this kit's `session-log` without either the name or the one-line description making that obvious — the only way to catch it is reading what each one actually does (a project's own hand-built RLS/access-control checklist and `verify-rls` is the same trap). Flag every apparent overlap to the project owner before installing: keep the existing one, keep the kit's, or merge into one. Never let both silently coexist doing the same job — that's how a project ends up with two things updating the same task tracker or writing the same kind of session log, discovered only by accident weeks later.

**The kit's templates land in `ae-kit-templates/`**, not in `templates/`. The name is prefixed precisely so it can't collide with a `templates/` the project already has for something else (email templates, scaffolding). **Every template path in this document is `ae-kit-templates/…`** — if you read `templates/` anywhere, it's a leftover and this is the correct path.

Once installed, `<project>/.claude/skills/` reads exactly like any hand-authored `.claude/skills/` — Claude Code (CLI, and cloud sessions working on a cloned repo) discovers skills purely by filesystem path, not by where the content originated.

Don't replace the copy with a skill-level symlink to a directory elsewhere on disk: it dangles after `git clone`. A physical, committed copy is what survives.

The end state is always the same: `.claude/skills/`, `.claude/agents/`, `ae-kit-templates/`, `scripts/` and `.ae-kit-version` exist at the project root. Everything below assumes that's already true.

**With one declared exception, and it isn't hypothetical.** A project can declare pieces out in `.ae-kit-excluded`, and the installer skips them — including `.ae-kit-version` itself. Before treating an install as broken because something from that list is missing, **read `.ae-kit-excluded`**: a piece listed there with its reason is absent on purpose, and treating that absence as a defect would halt the skill that runs first in every project. What's missing **without** being declared is a genuinely incomplete install.

## Procedure

### 0. Confirm the kit copy is current (new in v0.9)

`.ae-kit-version` at the project root, which `install.sh` writes automatically when the install completes cleanly, records which kit version this project is running. **Run `scripts/check-kit-current.mjs` before anything else** — it asks the kit's **remote on GitHub**, so this works on any machine, not only one that happens to have the kit checked out next door:

> **First: does this step apply?** If `.ae-kit-excluded` declares `.ae-kit-version` or `scripts/check-kit-current.mjs`, **skip this step entirely and say so** — don't report it as a failure, and don't report it as "up to date". That's the case of the repo that *produces* the kit: there its own `VERSION` is the source, not a copy to compare against, so the question "are you running the current version?" has no content. A normal project declares neither, and this step runs as always.

- **Exit 0 — current** → continue.
- **Exit 1 — behind** → the project's skills/templates have drifted from the kit (a skill was fixed or a template changed since this project last synced — the same silent drift that let two projects run a stale `setup/SKILL.md` for a week, caught only by hand-running `diff -rq` on 2026-07-19). **Before re-running the installer, do step 0a**: the install overwrites every kit file this project edited, so a fix living in one has to become a local adjustment first.
- **Exit 3 — no marker, or an unreadable one** → the copy step above wasn't run with the current kit's commands, or this project predates v0.9. Re-run the installer before continuing. For an already-set-up project it writes the marker and also replaces every kit file that differs from the kit's, so do step 0a first.
- **Exit 4 — ahead of the remote** → not "current": something was built in this project and never made it back to the kit. Say so; it is a lesson the return channel should be carrying.
- **Exit 2 — could not verify** (offline, no `gh`, no auth for a private kit repo) → report it as unverified and continue **without claiming the kit is current**. Not being able to check and checking clean are different answers.

This is a fast, mechanical check — don't skip it just because the skill files look fine at a glance; the whole point of versioning the kit is that this kind of drift is silent until checked.

### 0a. Before an update: a kit file the project edited becomes a local adjustment

Only for a project that already has the kit, before re-running the installer. **The installer overwrites kit files and never reconciles them**: a kit file this project edited is replaced like any other, and the report only lists it, with the git command that brings its content back. So whatever fix lives in an edited kit file is moved out of it first.

**Find them before installing.** If `.ae-kit-manifest` exists, `node scripts/check-local-adjustments.mjs` names every kit file edited since it was installed. `install.sh --dry-run` names them too, under "EDITED IN THE PROJECT" — without a manifest, by comparing against the published version `.ae-kit-version` names — but only the files the new version would replace, and nothing at all if it refuses. **If it cannot compare** (the marker is unreadable, or its version is not in the kit's published history), it lists every file it would replace as unknown: those are not edits, and none of them becomes a row. Stop and ask the project owner, or compare each one by hand against the commit that published that version (step 1 of `ae-kit-templates/local-adjustments.md` does that). **Each edited file becomes a row of `CLAUDE.md` → Local kit adjustments, following `ae-kit-templates/local-adjustments.md`** — the fix is written as prose in the row or moved to a local file outside the kit's paths, and the kit file goes back to its installed version. Then install, commit what the install wrote, and run `check-local-adjustments.mjs` until it exits 0. Nothing else carries a fix across an install.

**A project with an `.ae-kit-customized` list** (kept by older kits for files customized on purpose) converts every file it names the same way: nothing reads that list any more, and the guide deletes it once it names no file.

**If the installer refuses (exit 4)**, read what it names. Usually a kit file it would change has uncommitted changes — and right after a conversion, those changes are the conversion itself: commit it first (the row, the local files and the restored kit file together), stash only what is not yours to commit, and run it again. Otherwise the message says what kept it from asking git (for example, `GIT_DIR` set in the environment) and what to fix. Never write `.ae-kit-version` or `.ae-kit-manifest` yourself — they are the installer's statement of what it wrote.

**If the installer stops over the release notes (exit 5)**, it wrote nothing: a version between the one installed and the new one ships `release-notes/<version>.md` with steps under "Before installing", which it printed together with the rest of the notes. Do those steps first, asking the owner before any step that writes, moves or deletes anything in the project other than the kit files the installer replaces — for example `CLAUDE.md`, `STATUS.md`, `.gitignore`, `.gitattributes`, `settings.json`, a hook, `.ae-kit-excluded`, or a `git stash` or reset of the owner's work — or that acts outside the repo — a push, an issue, a call to an API, a secret — and before building or committing; then run it again with `--notes-done <new version>` — the exact x.y.z being installed, which the message names; any other version stops it again. A project whose `.ae-kit-version` is missing or unreadable but already has kit files sees every note from 0.37.0 on, and can be stopped by steps it already did: read them all. A single `--notes-done` confirms every "Before installing" step of every version printed, not one version's or one step's: pass it only when each of those steps is done or was already done before, never to get past the ones still pending. The steps under "After installing" are printed again when the install completes, and are done as the next paragraph says.

**When an install prints steps under "After installing"** — whether it stopped first or not, with one note or several — the order is this: first commit what the install wrote, `.ae-kit-manifest` included, after showing the owner the report and with their permission; a step that asks for something to go in that same commit (such as 0.37.0's `.gitattributes`) is done as part of it. Then do the "After installing" steps version by version, oldest first, and within a version in the order its note gives, asking the owner before each one under the same rule as the "Before installing" steps above. A step that asks to commit what the install wrote has only that part done once the commit is made: the rest of the step still stands — for example 0.38.0's first step also asks to recover the edits the report lists under "EDITED IN THE PROJECT", as step 7 of `ae-kit-templates/local-adjustments.md` says, and to tell the owner.

### 1. Run the interview (skip or shortcut anything already known)

**"Not yet" and "never" are both legitimate answers, not gaps to fill with a default.** A project that's barely getting started may genuinely have no backend, no typed language, no test framework, and no UI at all yet — that's a real state, tracked explicitly in `SETUP_CHECKLIST.md` section 0 as **Deferred** (not built yet, will be introduced later) or **Not applicable** (this project will never need it — requires the owner's explicit confirmation, never inferred). Don't force an interview answer toward the framework default just because a default exists; the default is what gets used *if and when* that piece is actually built, not a placeholder to accept as already true.

Ask, or infer from the existing repo if retrofitting:
- Backend/data store — **ask, don't assume a vendor.** Postgres-based options (a managed Postgres host, a self-hosted instance, Supabase, Neon, RDS) all satisfy this kit's requirements; so do non-Postgres stores, as long as the project can answer where migrations live and how per-user access is enforced. Record the answer as `{{MIGRATIONS_DIR}}` and the access-control mechanism. If nothing is built yet, ask whether this is the intended eventual stack (→ Deferred) or genuinely not applicable to this project (→ Not applicable, e.g. a local-only script with no persistence).
- How is a disposable sandbox obtained on this platform? Some offer ephemeral branches on paid tiers only; the universally-available fallback is a **second, separate instance** seeded with fake data (see `SETUP_CHECKLIST.md` template's reference block). If on a paid plan, Preview Branches can be used instead.
- Does any table have per-user or per-role access control (Postgres RLS, or the equivalent in another backend)? If yes, `verify-rls` applies — during setup, point it at this project's actual role model (which roles exist, which tables/rows each can touch) rather than leaving it generic; see that skill's own file for what it needs filled in. If there's no database yet at all, this is Deferred, not a "no."
- AI-native features — any model calls in the shipped product, not just Claude writing the code? If yes, ask where they run (serverless functions, a backend service, the client) — that's where the eval harness attaches.
- Frontend — default: React + Vite.
- Does it have a UI at all? (Some projects are backend/data-only.)
- Package manager — default: npm.
- Migration folder and tool — wherever this project's schema migrations live becomes `{{MIGRATIONS_DIR}}`, and the environment variables its client needs become `{{DB_ENV_VARS}}` in `.env.example`. Ask; don't fill either from a default. The kit's schema-only check autodetects the common conventions, but the templates need the real value written in.
- Commit message convention — default: a type prefix plus a descriptive summary (`feat:` / `fix:` / `chore:` / `refactor:`). If retrofitting, check `git log --oneline -20` first to see whether a different pattern is already in use before asking — don't assume the default just because nobody was asked. Whatever's confirmed here becomes `{{COMMIT_MESSAGE_FORMAT}}` in `CLAUDE.md`'s Git conventions section.
- Branch policy — default: isolation follows concurrency. A branch or worktree exists only while two writers work at once; a single session commits directly to the tracked branch. Ask directly whether this project already has a different policy, such as one branch per task — don't assume the default without asking, even if git history doesn't make it obvious either way. Whatever's confirmed here becomes `{{BRANCH_POLICY}}` in `CLAUDE.md`'s Git conventions section.

  The answer is also one of three words, and the word decides two edits nobody should make by hand: `delegate` (units are built by subagents in worktrees — `.gitignore` must ignore `.claude/worktrees/`), `single` (one writer at a time — the template's "Delegating is the default" line comes out of `CLAUDE.md`), or `other` (a policy of the project's own that is neither, such as one branch per task — neither file is touched; what it needs is asked, not defaulted). **The kit's default is `delegate`**: the template ships the delegation line, so a project that gives no other answer delegates. A single-writer project is `single` whether its `CLAUDE.md` is new or a mature one found in retrofit; `other` is only for a different policy of its own. Run `node scripts/apply-branch-policy.mjs <single|delegate|other>` from the project root **on the `CLAUDE.md` freshly generated from the template, still in English, before translating it into the project's language** (2a step 2), and relay what it prints. When translating afterwards, **leave the delegation line in English**: it is configuration, not prose, and a later `single` finds it only verbatim. The script never guesses which line delegates: it recognises only the template's line, word for word. Exit 0 means the project is consistent with the policy; 1, a usage problem it explains; 2, a file it could not read or write; **3, "could not verify"** — `CLAUDE.md` does not carry the template's line verbatim (a mature or already-translated file), so the script lists every line that mentions a worktree or an `ai/` branch and changes nothing in `CLAUDE.md` (`delegate` still writes `.gitignore` first). Exit 3 is never a pass: read the listed lines and settle them — for `single`, remove whatever still tells the agent to delegate; for `delegate`, confirm the file asks to delegate, or add the template's line in English — then say what you did. **Do not rerun the script to confirm a fix**: after a hand edit, or on a second `single` run once the line is gone, exit 3 is the expected result, not a sign the fix failed — what closes it is the edit you report. For `single`, also write the single-writer policy into the Branch policy line yourself: the script removes the delegation line but does not write the project's own words for it.
- Who pushes, and the delivery channel — ask both; infer neither. Who may push to the tracked branch becomes `{{PUSH_POLICY}}`. The delivery channel is where this project's production lives: the deploy target, the store, the published repo. Name it concretely, because a push that reaches it is the owner's call (class A in `ae-kit-templates/decision-classes.md`), and every other push is not. The answer becomes `{{DELIVERY_CHANNEL}}` in `CLAUDE.md`'s Git conventions section. Check the two answers against each other: if pushing to the tracked branch already reaches the channel (a deploy on every push to main, for example), `{{PUSH_POLICY}}` must say so and exclude those pushes — "Claude pushes, except what reaches the delivery channel" — because `ship` follows `{{PUSH_POLICY}}`. If the project has no production yet, write `none yet` and say what the channel will be once it exists.
- Testing — default: Vitest (+ Playwright if there's a UI). If no test framework is installed yet because there's no code to test yet, that's Deferred, tracked in section 0 — don't install a test harness with nothing to exercise just to check a box early.
- **Suite command — ask for it, or read it from the project; never invent one.** The single command that runs every suite, becoming `{{SUITE_COMMAND}}`, the Suite command line of Stack. It is not R4's `{{TEST_COMMAND}}`: that one runs in the main checkout on every push, lint included, and must stay fast; this one runs inside a unit's worktree, once per integration, and starts clean. In a project with dependencies or a build step it starts clean — for example `npm ci && npm run build && npm test` — because `integrate-unit.mjs integrate --verify` runs it inside a unit's worktree, where a dependency folder or a build output left from an earlier run would let a suite pass on files the commit no longer produces. Retrofitting, read it from the CI workflow or the package scripts and confirm it with the owner. With no tests yet it is `TBD — deferred`, like Testing: until it has a value, units are built by a single writer in the main checkout instead of delegated, because `build` does not integrate a delegated unit without it.
- **Project language — ask outright; never infer it from the language of the conversation.** Which language should this project's own artifacts be written in: `CLAUDE.md`, `SETUP_CHECKLIST.md`, `STATUS.md`, task files, scope docs, session logs, and everything you write into them from now on. **If the answer is Spanish, it means Mexican Spanish, with full orthography — every accent and diacritic, never stripped to ASCII.** Record the answer in `CLAUDE.md` under a `## Language` heading, in one line: that file is re-read at the top of every session, so it needs no new mechanism to be found.

  **The kit itself stays in English regardless** — skills, scripts, templates and their output. It is shared infrastructure headed for a public repo, and one language is what keeps it readable. So a Spanish-speaking project will see English tool output alongside its own Spanish documents; that is the deliberate trade, not an oversight. The one exception is the control center page (`ae-kit-templates/control-center.html`): it carries its texts in English and Spanish, and its language is asked the first time the control center is created, not here.

  Keep the **three** languages apart: the conversation's (the owner's own setting), the project's artifacts (this question), and the kit's (English, fixed).
- **Does the owner read code? — ask once; never assume.** Record the answer as `{{OWNER_READS_CODE}}` in `CLAUDE.md` → Who reviews, and how. It decides how much SQL and diff is shown alongside the reviewable artifact, not the artifact bar itself.
- Current maturity — prototype / pre-users / live-users. This is a real-world fact the project owner must state; never infer it.
- **Does this project contribute lessons back to the kit? — ask outright, and take no default.** At the end of each session, `session-log` can emit a de-identified payload of what this project learned (see `emit-lessons.mjs`), which is how the kit improves from real use instead of from speculation.

  **Why this is asked rather than assumed:** a project's engineering lessons are arguably its owner's, not the kit's. Something like *"this project ran for weeks with production credentials hard-coded"* is still about them even with every name stripped, and the kit's destination is a shared artifact. **"Yes" by default makes a client a donor without knowing it; "no" by default kills the channel silently** — so the only honest move is to make someone answer. Write the answer to `.ae-kit-contrib` at the project root as exactly `yes` or `no`. Leaving the file absent is a valid interim state and behaves as "don't emit," but it keeps getting raised until answered; it is not a quiet no.

  If the answer is yes, mention what actually travels: fixed fields with hard length caps, no free text that can hold a quote, a path, an id, or a name, and a deny-list built from this project's own git authors, remote, and client name. The emitter rejects a payload rather than cleaning one.

### 2. The rules table is cross-checked against `.ae-kit-excluded` — applies to both 2a and 2b

**This applies to both branches below, greenfield and retrofit, whenever `CLAUDE.md` is written or extended.** It sits up here on purpose: written inside one of the two, the other ignores it — and the branch that needs it most is retrofit, which is the one that runs in a repo with exclusions already decided.

Before writing the table, **cross-check every row against `.ae-kit-excluded`, in both of its columns**:

- **The trigger.** A row whose trigger names a `script:`, `skill:`, hook command or CI command the project declared out **is not written** — it's recorded in `SETUP_CHECKLIST.md` as not applicable, with the same reason the list gives. Copying it anyway isn't cosmetic: the trigger resolves against files that aren't there, and the **freshly configured** project's pre-commit and CI land red over template rows nobody edited. Note the `script:` grammar since 0.30.0: it names the file **and the skill that runs it** (`script:scripts/check-pendings.mjs:open-session`), and the checker reads that skill's `SKILL.md` to confirm it is named there. So a `script:` row is also wrong when the skill running it was declared out — the file can be present and still have no caller.
- **The verification.** A row can have a trigger that does exist while being verified by something the project declared out — the kit-sync rule is the case: it fires on `skill:open-session`, which is installed, and is verified by comparing `.ae-kit-version` against the kit's `VERSION`, which may not exist. `check-rule-triggers.mjs` **does not look at that column** (it only requires it to be non-empty), so such a row lands green and is enforced by nothing. Rewrite the verification to whatever genuinely applies in this project, or drop the row. A rule nothing triggers is a rule enforced by memory — and one that claims to be verified by an absent file is worse, because it looks covered.

- **The CI rows are conditional on a CI workflow that the kit does not ship.** Three template rows name `ci:ci.yml:…` literally — the ones for `check-rule-triggers`, `check-skill-outputs` and `check-inline-rules`. The kit ships **no** `ci.yml`: only the gitleaks workflow and, for a database project, the migrations one. So writing those rows into a project that has no CI job for them leaves the brand-new project red from its first commit, over rows nobody wrote by hand — the exact failure this section exists to prevent, arriving through a different door than the exclusion list. Either create the job first (a `run:` step whose command contains each checker's name; §4c of `SETUP_CHECKLIST.md` says what it has to contain) and make the rows name that workflow's **real filename** instead of `ci.yml`, or do not write the rows yet and record them in `SETUP_CHECKLIST.md` as pending. `check-rule-triggers.mjs` never reads `.ae-kit-excluded`, so a row stays red for exactly as long as the row exists: the way to not have a rule is to not write its row.

- **The `R36` row stands on a hook, and the hook stands on the collector.** Its trigger is `claude-hook:SubagentStop:collect-subagent.mjs`, which reads `.claude/settings.json` — the declaration the installer writes. **If `.ae-kit-excluded` declares `scripts/collect-subagent.mjs`, the installer writes no hook and the `R36` row is not written**: the exclusion explains the missing file, never a rule still claiming a trigger that is not there. And if the collector was installed but the install reported a conflict on `settings.json`, the hook is not declared yet either — write the row once the block the installer printed is in the file, not before, or the brand-new project lands red over a row nobody edited. Note what it does *not* accept: `settings.local.json` is never read, so a hook declared there leaves the row red on every machine but the one that wrote it.

- **Numbering gaps stay unfilled.** Keep each row's template number, even when rows above it were dropped; don't renumber. `R26` is absent from the template because only the kit's own repository holds it, and a shared number with the kit's table means a shared rule.

**"Dropping the row" means not writing it when generating from the template — never deleting a rule from a `CLAUDE.md` that already exists and that a team relies on.** In that case 2b step 5's rule holds: additive edits, and the contradiction is **flagged** to the owner rather than resolved unilaterally. Omitting a row that never existed and deleting one somebody wrote are different acts, even when the result on disk looks similar.

### 2a. Greenfield: install everything fresh
1. Confirm `.claude/skills/` and `ae-kit-templates/` exist at the project root — the installer leaves them there. If either is missing, stop and ask for the install to be run first.
2. Generate `CLAUDE.md` from `ae-kit-templates/CLAUDE.md.template`, writing the result to the project root as `CLAUDE.md` (drop the `.template` extension), filling in the interview answers — including the Git conventions section with the confirmed commit format and branch policy. **Generate it in English first, run `scripts/apply-branch-policy.mjs` with the policy's word on that English file, and only then translate it into the project's language**, keeping the delegation line in English if it survived (see the branch-policy question above). Any Stack field with a genuinely Deferred or Not applicable answer gets written as `TBD — deferred` (or similar), never a guessed default value standing in for a real decision.

   Before writing the rules table, apply the **cross-check against `.ae-kit-excluded`** described in section 2, just above 2a.

   **Local kit adjustments is generated empty**: the table keeps only its filler row (`| — | — | — | — | — |`), because a new project has edited nothing of the kit. Write no example row and no second table under that heading, not even in a comment — `check-local-adjustments.mjs` reads every table there as adjustments. When translating, the heading may become `Ajustes locales al kit` and the columns `Qué modifica`, `Cómo se aplica`, `Archivos locales`, `Issue`, `Fecha` — the Spanish names the checker accepts. Use exactly these: a column with any other name is rejected, but a heading with any other wording is not recognized at all, so its rows would never be checked and nothing would say so. When in doubt, keep the heading in English.
3. Copy `ae-kit-templates/.env.example` to the project root as `.env.example`, and confirm `.env*` (except `.env.example`) is in `.gitignore` before anything else touches real credentials.
4. Create `tasks/` (empty), `PENDINGS.md`, `/logs/sessions/` (empty — the first session log creates its own month folder inside it), and `STATUS.md` at the project root from their `ae-kit-templates/` sources (same drop-the-`.template`-extension rule), with `maturity:` set from the interview. **Do not write `TASKS.md`, `BACKLOG.md` or `TASKS_ARCHIVE.md` by hand** — they are indexes generated from `tasks/` by `scripts/generate-task-index.mjs` (`BACKLOG.md` lists the tasks in `backlog` and `todo`); run it once so the empty indexes exist.
5. Generate `SETUP_CHECKLIST.md` at the project root from `ae-kit-templates/SETUP_CHECKLIST.md.template`, with every box unchecked, **and section 0's tri-state markers set accurately from the interview answers** (Not applicable / Deferred / Active per optional piece — see step 1 above) before checking anything else off live as it's actually confirmed in this same session (repo initialized, branch protection set, sandbox created, etc.). Don't check a box you haven't verified, and don't mark something Active in section 0 unless it's genuinely built and in place right now.
6. `ae-kit-templates/` can stay at the project root afterward (harmless, just the raw sources) or be deleted once every generated file exists — either is fine.

### 2b. Retrofit: detect before assuming
1. **Read the existing repo first** — package.json/requirements, existing test setup, existing DB config, existing docs — before running the interview, so questions aren't asked about things that are already obvious.
2. **Before anything else, scan git history for already-committed secrets — with a real content-scanning tool, not a filename grep.** Run `gitleaks git .` (installed via brew/go/binary) against the full repo. A filename-based check (looking only at `.env`, `.pem`, `service-account*.json`, etc.) is not sufficient on its own — a real leak has already been found sitting in a plain `docs/*.md` file, complete with a written "don't commit this" warning right next to it that got committed anyway. Secrets hide in documentation, READMEs, comments, and seed scripts just as often as in the files you'd expect, and a human-written warning comment is not a safeguard. **If `gitleaks` itself can't be installed in the current execution environment** (e.g. a cloud agent sandbox with restricted network access to GitHub or the Go proxy — confirmed to happen), fall back to an equivalent full-content scanner across the same full history (`detect-secrets` plus a manual regex sweep of the complete diff, for example) — the requirement is a real content scan across every commit, not that specific binary; note in `STATUS.md` or the session log which tool was actually used and why, so it isn't silently rediscovered next time. **If anything turns up, stop and tell the project owner immediately that the credential must be rotated or disabled at its source (Supabase, the API provider, etc.) before setup continues.** Removing the file from tracking or history afterward is cleanup, not remediation, and does not undo the exposure — do not let this get bundled in as just another checklist box ticked in passing. "The app no longer uses it" is not the same as "it's disabled" — confirm the credential itself is dead. Once clean, install `gitleaks` as a pre-commit hook (Husky or the `pre-commit` framework) *and* copy `ae-kit-templates/gitleaks-workflow.yml.template` to `.github/workflows/gitleaks.yml` (create the `workflows/` folder if it doesn't exist, merge in if other workflows are already there) — the hook blocks a secret before it's committed at all; the GitHub Action is the backstop that catches anything the hook missed (unhooked clone, `--no-verify`, a direct push). Both matter; neither alone is sufficient. The GitHub Action runs on GitHub's own runners regardless of what environment ran the local scan, so it's unaffected by any network restriction that forced a fallback tool above.
3. **If the project has a database, check whether its schema was ever built ad hoc** — compare what the platform reports as applied against what actually exists in `supabase/migrations/` locally. A project with applied changes but no (or an incomplete) local migrations folder means schema was edited directly against the database at some point, with nothing reproducible left in git. If so, baseline it now: `supabase init` → `supabase link --project-ref <ref>` → `supabase db pull`. This isn't optional or deferrable — the Sandbox section of `SETUP_CHECKLIST.md` cannot be completed without it, since a reproducible sandbox depends on reproducible migrations.
4. Confirm `.claude/skills/` and `ae-kit-templates/` exist at the root, same as greenfield — if the project already had its own `.claude/`, the installer doesn't replace it: it adds the new skills, and replaces any file at a path the kit ships that differs from the kit's version. Apply there the overlap review by name AND by purpose described above — before the install: a project skill at a kit skill's path is moved off it first, never the kit's copy renamed after. **A kit file the project edited by hand** — a skill or script changed in place to fix something the kit did not ship yet — is not resolved by keeping or overwriting it: it becomes a row of `CLAUDE.md` → Local kit adjustments (add the section from the template if a mature `CLAUDE.md` has none), following `ae-kit-templates/local-adjustments.md`, before the `R38` hook is wired. Overwriting it loses the fix; keeping it leaves the next install to lose it silently.
5. **Check whether `CLAUDE.md` already exists and is doing real work before generating anything.** A stub, a placeholder, or nothing at all → generate `CLAUDE.md` from `ae-kit-templates/CLAUDE.md.template` as usual (dropping the `.template` extension, written to the project root), **applying the cross-check against `.ae-kit-excluded` from section 2** — this is the branch that runs in a repo with exclusions already decided, so copying the whole table leaves `check-rule-triggers.mjs` red from the very first commit — reflecting the *actual* existing architecture, commit convention, and branch policy rather than the default assumptions, if they differ — see the interview's commit-convention and branch-policy questions above. Any Stack field with a genuinely Deferred or Not applicable answer gets written as `TBD — deferred`, same as greenfield. A mature, already-working `CLAUDE.md` (working rules, an established process, real project-specific content a team already relies on) → do **not** regenerate it from the template; that would silently destroy content nobody asked to lose. Instead, read the existing file in full and make a targeted, additive edit: add a `## Skills` section (or extend an existing one) documenting how the newly added generic kit skills (`open-session`/`prototype`/`scope`/`design`/`adversarial`/`build`/`verify-tests`/`verify-evals`/`verify-ui`/`verify-rls`/`commit`/`code-review`/`ship`/`session-log`, plus `setup` itself) relate to any of the project's own custom skills — which generic skill maps to which step of the project's existing workflow, and which custom skills stay bespoke because nothing in the kit covers their purpose. Confirm the existing Git conventions section already matches what the interview confirmed (commit format, branch policy); note the difference rather than overwriting it if it doesn't. A `CLAUDE.md` generated here follows 2a step 2: English first, the script, then the translation. A mature `CLAUDE.md` is not regenerated, so the script almost always exits 3 on it — it does not carry the template's line verbatim. Run it anyway with the policy's word (`single` for a mature single-writer file too; `other` only for a policy of the project's own, such as one branch per task): with `delegate` it still writes `.gitignore`, and in both cases it lists the lines that mention a worktree or an `ai/` branch. Read them, settle them by hand as the branch-policy question says, and tell the owner what changed — exit 3 is not a pass. If the project has other pre-existing top-level docs the kit doesn't generate (a `ROADMAP.md`, `SYSTEM.md`, or similar), don't restate their content in `CLAUDE.md` — add one line per doc pointing to it and naming what it's for, the same way `CLAUDE.md` should point to `TASKS.md`/`BACKLOG.md` rather than duplicate them. Every apparent purpose overlap between an existing doc and a kit-generated one (most commonly: an existing roadmap/planning doc vs. the kit's own `TASKS.md`/`BACKLOG.md`) gets flagged to the project owner before assuming which one governs going forward — the same discipline as the skill-overlap review above, just applied to documents instead of skills.
6. Generate `SETUP_CHECKLIST.md` and **go through it item by item against what actually exists today** — check only what's genuinely already in place (e.g., if strict typing is already on, check it; if there's no sandbox at all, leave it unchecked and flag it as the first real task). **Set section 0's tri-state markers first, honestly, before working through the rest** — a project with no Supabase, no typed language, no RLS, and no test framework isn't necessarily an incomplete retrofit; if those pieces genuinely don't exist in the codebase yet, mark them Deferred (or Not applicable, with the owner's confirmation) rather than flagging every corresponding section as a missing gap to close today. The output is a to-do list of what's actually due now, not a rubber stamp and not a demand to build stack pieces the project doesn't need yet.
7. Do not touch existing task-tracking history (e.g., an existing Notion setup) as part of this step — that's a separate, optional migration (see the framework doc's retrofit-vs-migration split). Start task tracking fresh in `tasks/` going forward regardless; the indexes are generated from it.

### 2c. Setup fires again later — introducing a stack piece is a setup event

**This skill does not only run once.** Almost no project has every piece of its stack on day one, and `SETUP_CHECKLIST.md` section 0 tracks each optional piece as Not applicable / Deferred / Active. The moment a piece marked **Deferred** is about to become real — the first migration, the first typed file, the first test file, the first table with an owner column, the first UI component, the first model call — **stop before that commit lands**, flip its status to Active, and satisfy that piece's checklist section *first*.

For example: strict typing from the first typed file; an access-control policy documented from the first table with an owner column; a test harness wired before the first meaningful function ships.

This is the same plan-first discipline `scope` applies to features, triggered by a new capability instead of a new task. `CLAUDE.md` states it as a rule; this step is where it is carried out.
### 3. Confirm completion
Setup is only "done" once every box in `SETUP_CHECKLIST.md` is checked or legitimately left unchecked under a Not applicable / Deferred section-0 status — not when the interview finishes. If closing out setup reveals work that can't be completed in this session (e.g., a sandbox that needs to be created outside the agent's reach), leave those boxes unchecked and record them as the top priority in `STATUS.md`'s "Next session" section.

## Output
`CLAUDE.md` (with Git conventions filled in, Stack fields marked `TBD — deferred` where genuinely undecided), `SETUP_CHECKLIST.md` (section 0's tri-state markers set honestly, and the rest accurately reflecting real state), `.env.example` and a confirmed `.gitignore` entry, the already-copied `.claude/skills` directory, `.ae-kit-version` confirmed present and current (written by step 0 or the copy step, not regenerated here; **absent and declared in `.ae-kit-excluded` counts as confirmed**, not as a missing deliverable), and (for greenfield) empty task-tracking files — `tasks/`, `PENDINGS.md`, `/logs/`, `STATUS.md` (with `TASKS.md`/`BACKLOG.md`/`TASKS_ARCHIVE.md` generated, never created by hand) — ready to use, or (for retrofit) a concrete, prioritized list of what's actually missing right now, distinct from what's simply deferred to a later stage of the project.
