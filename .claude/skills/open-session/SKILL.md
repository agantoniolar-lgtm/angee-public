---
name: open-session
description: Use at the start of a working session — the project owner says something like "open session," "let's continue," "what's next," or otherwise picks work back up — or any time there's doubt about current project state. Reads STATUS.md, the latest session log, TASKS.md, and BACKLOG.md, then recommends one concrete next action instead of just reporting status. The session-opening counterpart to session-log, which closes a session.
---

# Open session

## When this fires
The start of a working session, on a signal like "open session," "let's continue," "what's next," or simply picking a project back up after time away — this is the mirror of `session-log`, which runs at the *end* of a session. Also worth running any time there's doubt about where a project actually stands, even mid-session.

## Procedure

1. **Read `STATUS.md` in full.** `maturity`, "Next session," "Last session," and the "Decisions" table together are usually enough to reconstruct where things stand without opening anything else.
2. **Read the most recent session log**, for anything more granular than STATUS.md's summary — specific files touched, specific decisions made and why. Sessions live in `/logs/sessions/<YYYY-MM>/`, one folder per month: take the **highest month folder**, then the highest date inside it. Both sort correctly as plain text, so `2027-01` beats `2026-12` without any date parsing.

   Two cases worth handling rather than tripping over:
   - **The newest month folder is empty** (it was created and the session was never written). Fall back to the newest month that actually holds a file, instead of reporting that there are no logs.
   - **A `session-*.md` sits loose in `/logs/`**, outside `sessions/`. That is a project whose logs were never migrated to the month layout. **Say so** — don't silently read it and don't silently ignore it — and point at `ae-kit-templates/migrate-logs-to-months.md`.

   **Then find the control-center line the last close wrote** (`session-log` step 1b): `grep -m1 -E '^control center:' <that log>`. Only a line that exists and contains `not done` becomes a flag in the brief, with the log's path: something the close could not do on the page — record a decision, finish the migration, a page not republished — is still waiting. A line without `not done` is not repeated, and no line at all is not a flag: logs written before the kit had this line carry none. **A `not done` about recording decisions is dropped when step 5b of this opening ran its query and left no decided card unrecorded** — that work is done now; one about the migration or a republish is repeated anyway, since step 5b does neither and only the close resumes the migration. Which way it goes is settled when the brief is written, after step 5b. This reads the log only; the page itself is step 5b's.
3. **Read `TASKS.md`.** This file should be short by construction (only `in progress`/`waiting on owner`). Note every entry's status and its `updated:` date. **Then read `BACKLOG.md`** — since 0.29.0 it is a generated index of the tasks in `backlog` (no scope written yet) and `todo` (scoped, awaiting a turn), not a hand-kept list.
4. **Read `BACKLOG.md`.** Not to promote anything yet — just to know what's waiting in case `TASKS.md` turns out to be empty.
5. **Check for staleness, or a prior session that wasn't closed cleanly, and surface anything found rather than silently working around it:**

   > **Before running anything on this list: checks whose script the project declared out are not run.** Several checks below call a script in `scripts/`, and a project may have declared any of them in `.ae-kit-excluded` — in which case the installer deliberately never put it on disk. **Read that list first, skip the checks whose script is declared, and say so once**, naming which ones and with what reason: neither as a failure nor as "up to date". What is **not** an escape hatch: a script that is missing **without** being declared — that is an incomplete install and gets reported as one. This rule covers every check on the list.
   - A `TASKS.md` entry marked `in progress` or `waiting on owner` whose `updated:` date is older than the most recent `/logs/` file's date — the task wasn't touched during the session that log describes, which usually means it stalled or was abandoned without being recorded.
   - `TASKS.md` listing a task whose file says `done` — the index was not regenerated, which usually means the last `session-log` did not close cleanly. Report it; do not fix it here.
   - **Is this project running the current kit — run `scripts/check-kit-current.mjs`.** *(This check also falls away when what's declared out is `.ae-kit-version` rather than the script: with no marker there is nothing to compare. That's the case of the repo producing the kit, where its own `VERSION` is already the source.)* It asks the kit's **remote**, not a copy on local disk, so the answer is the same on any machine. Exit `1` means behind: **update before starting any work** — and since the install overwrites every kit file that differs, a kit file this project edited is first turned into a row of `CLAUDE.md` → Local kit adjustments (`setup` step 0a, with `ae-kit-templates/local-adjustments.md`), then the kit is installed and what it wrote is committed. The installer prints the release notes of every version it jumps, and stops with exit `5`, writing nothing, if one asks for steps "Before installing": the session does those steps, **asking the owner before any step that writes, moves or deletes anything in the project other than the kit files the installer replaces — for example `CLAUDE.md`, `STATUS.md`, `.gitignore`, `.gitattributes`, `settings.json`, a hook, `.ae-kit-excluded`, or a `git stash` or reset of the owner's work — or that acts outside the repo — a push, an issue, a call to an API, a secret — and before building or committing**, and doing it only once approved; only when every step is done does it re-run the installer with `--notes-done <new version>`: one flag confirms every "Before installing" step of the whole range, so it is never passed while one is left. Exit `4` means *ahead* of the remote — not a pass, but the anomaly that something built here never made it back. Exit `2` and `3` mean the check could not be made; report that plainly and **never restate it as "up to date"**.
   - A dirty or unpushed git state left over (uncommitted changes, or a branch that was never merged) — check with `git status`/`git log`, read-only. This is a signal to report, not to act on. **The single exception is the ledger commit in the next bullet**; apart from that one file, never run `git add`/`git commit`/`git push` as part of this skill. This check runs before step 5b, so it does not see what 5b writes: the brief's control-center line names what 5b left uncommitted (the task-log entries it wrote, a new `.ae-control-center`), for the session's next commit to carry.
   - **Evidence of verification that never got committed — the same `scripts/check-deploy-verified.mjs`, exit `4`.** The ledger line proving a push was verified is written *after* `ship` already committed and pushed, so **the last line of a session** stays in the working tree uncommitted.

     **This skill settles it, as its first act: commit `logs/deploy-checks.md` on its own, with a message naming the SHA it covers — and do not push it.** It travels out with this session's first real push, which gets verified normally. This is the one commit this skill is allowed to make. Its message ends with `Task: none`, because the ledger belongs to no task. It is not the skill's only write: step 5b also writes decisions into task logs (`scripts/task-log-append.mjs`), writes to the control center page, and may write `.ae-control-center` — and commits none of them.
   - **A push that was never verified — run `scripts/check-deploy-verified.mjs`.** Exit `1` means the commit sitting on the tracked branch has no resolved line in `logs/deploy-checks.md`: the previous session pushed and never confirmed the remote came back green. Surface it as the first flag and settle it (run `check-deploy-status.sh <sha>`) before recommending new work.
   - **What each task in progress left alive — run `scripts/integrate-unit.mjs status <task>`** for every task whose file says `in progress`, reading the exit code from the command, never through a pipe. This only reports, it never stops the session: `1` names what is out of place — worktrees or unit branches still alive, work not integrated, units whose record is wrong — each with what to do; `2` says the task, or the checkout, could not be read (a detached HEAD or an operation halfway through gives `2` for every task: say that once). Surface them as flags. The task's next `ship` clears only the leftovers of units already integrated (its step 1b); anything else waits for the session to act on it, or holds that `ship`. Tasks in any other state are not checked here: a task closed before units recorded their commit would report findings nobody needs to act on.
   - **Pendings that have outlived a decision — run `scripts/check-pendings.mjs`.** Exit `1` means something has been carried three or more separate sessions and is still `open`. Surface each one with who can close it, and force the choice this session: promote it to a task, hand it to whoever can actually close it, or drop it in writing. Do not carry it a fourth time. Then increment nothing here; `session-log` owns the counter.
   - **`STATUS.md` keeps its shape — run `scripts/check-status-shape.mjs`.** Exit `1` names what broke: report it. Exit `3` means the file still has the old layout; read it anyway, say it needs migrating, and do not stop the session over it. A warning about more than 15 decisions is reported, not fixed here.
   - **Rules with no trigger — run `scripts/check-rule-triggers.mjs`.** Exit `1` means a rule in `CLAUDE.md` names no trigger, or names one that no longer exists (a hook deleted, a skill renamed, a workflow moved). Report it.
   - **Subagents saved more than once — count the folders under `logs/subagents/` that hold an `output-2.md`** (`ls logs/subagents/*/*/output-2.md 2>/dev/null | wc -l`). A subagent that was saved again with a different reply keeps each later reply beside the first, as `output-2.md`, `output-3.md`. At 15 or more, say so once: that is the sample agreed for deciding whether a later reply should replace the first instead of sitting beside it. No `logs/subagents/` means zero; say nothing.
5b. **The control center: watch it when the project has one, offer it when it does not.** The control center is the private claude.ai page where the owner takes class A decisions (`ae-kit-templates/control-center.md`); a project registers it in a `.ae-control-center` file at the repo root. Take the first case that fits the file. This step never stops the opening, and runs before the brief: the brief stays the last thing written, and its control-center line is one line that reports this step.

   - **A file with `url` and `lang` — the common case: exactly three calls, and nothing else is read.**
     1. One `ToolSearch` that loads both tools at once: `select:ArtifactComments,ArtifactData`.
     2. `ArtifactComments` `watch` with the `url`. Say "watching" only when the result says the watch connected; an "arming" line is not a watch yet.
     3. `ArtifactData` `query` on `decisions`, `where: [["status", "==", "decided"]]`.

     **If the query returns no card without a `logEntry`** — only a non-empty string counts as one; no field, `null` or `""` is unrecorded — the guide is not read, and the line is `control center: watching; nothing pending`. **Only when some card is unrecorded**, read section 2 of `ae-kit-templates/control-center.md` ("Processing what was decided") and run it on those cards, from the marker read of its step 1 on, without repeating the query. A decision recorded here unblocks work, and step 6 reads it that way; a card that could not be recorded is a flag.

     A part that cannot run — a tool that does not load (a subagent or a print session has neither), a call that fails, a page that says it is read-only — is **not done**, with why. A failed watch does not skip the query. **A failed query is never "nothing pending":** the line says the decisions could not be checked, and why. The line gives the watch, then `nothing pending` or each decision recorded and what it unblocks, and the task logs written — left uncommitted, since step 5's git check ran first.
   - **A file with `declined` and no `url`:** no call at all, not even the `ToolSearch`. One line, "control center: declined on <date> — say so to create it", and nothing is asked. Deleting the file, or the owner asking for the control center, brings the offer back.
   - **A file that does not parse, or lacks `url` or `lang` without `declined`:** no call; say so in one line, as a flag.
   - **No `.ae-control-center`: offer to create it**, without holding the opening. The brief goes out whole, recommendation included; the offer is its last line, one question in the chat — the class A rule puts a question on a card only when there is a page to put it on (`ae-kit-templates/decision-classes.md`). It is the owner's call, class A, and it asks three things at once:
     > No control center is registered. (a) create a new private page, (b) adopt a page you already have — give its claude.ai link; I republish the kit's page over it, which replaces how it looks; its decisions stay, and its `meta/project` is rewritten with this project's name and language and the page's marker. Anything else in its database stays where it is, and the page no longer shows it. I mark its old decisions so they are not written into a task log again (any not found in a task log in the kit's `card <id>` form, I ask you about first) — or (c) not now. And in which language, `en` or `es`?

     What this path writes in the end is one JSON object, which holds no secret — the page is private, and its link is not a credential:

     ```json
     { "url": "https://claude.ai/artifact/<id>", "lang": "es", "name": "<project>", "productionRef": "origin/prod" }
     ```

     `url` (the page's claude.ai link) and `lang` (`en` or `es`) are required; `name` defaults to the repo folder's name, and `productionRef` is only for a project that names a ref holding what is in production.

     **If the session cannot run it** — no Artifact tool or no `ArtifactData` (a subagent or a print session has neither), or no `ae-kit-templates/control-center.html` in the project — the line says that instead ("control center: none registered; creating it not done — <why>") and nothing is asked. **No answer this session:** nothing is written, and the next opening asks again. **(c) "not now":** write `.ae-control-center` as `{ "declined": "<date -u +%F>" }`. The answer can come at any point of the session; the path below runs when it does. **The language is normalized first:** `es`, `es-MX`, español, Spanish, castellano → `es`; `en`, `en-US`, English, inglés → `en`. Any other answer, or none, is asked again before anything is published. Every part that cannot run is reported as **not done**, with why, never as done.
     - **(a) A new page.** First load the `artifact-capabilities` skill, which the Artifact tool asks for before any `capabilities`. Then publish with the Artifact tool: `file_path: "ae-kit-templates/control-center.html"`, no `url`, `icon: "dashboard"`, `capabilities: {"db": {}, "user": {}, "comments": {}}` — `comments` in its full form, because the page sends the session its notices. The result gives the page's URL.
     - **(b) Adopt the owner's page.** Everything is checked and marked **before** the template goes over the page, so an adoption cut short leaves the owner's page as it was, never a new page nobody watches. 1) The Artifact tool `read` with that `url` — a publish to an artifact this session has not read is refused. If the result does not say the owner is a writer, say so and offer (a) instead. 2) Find the old decisions — unmarked, the guide's section 2 would write each of them into a task log as a decision the owner took today, for good. `ArtifactData` `query` on `decisions`, `where: [["status", "==", "decided"]]`, keeping those with no `logEntry` — no field, `null` or `""`; only a non-empty string counts as recorded, as in the guide's section 2. Look each one up in the task logs with the guide's anchored search (section 2, step 3), run with `grep -rlE` over `logs/tasks/` instead of one file: the id goes in through the quoted heredoc and with its regex metacharacters escaped, never interpolated unquoted into the shell — it is data from the owner's page — and anchored, since `T5-F1` would otherwise match `card T5-F12`. One that appears was recorded and is marked; the ones that appear nowhere go back to the owner as one short list — "these N decisions on your page are not found in any task log in the kit's `card <id>` form: mark them as old?" — and are marked only on a yes; on a no, section 2 records them, as the owner chose. Also `query` the cards with `status` `open` or `upcoming` and keep those with no `order`. A query that fails stops the adoption, as in step 4. 3) Mark them: `logEntry: "legacy-pre-kit"` on each card to mark, and in the same writes an `order` (`date -u +%s`, consecutive for several) on each open or upcoming card without one, so the page does not hide it. Everything goes through `ArtifactData` `batch`, at most 50 `update`s per call, each pinned with `if_version`; a refused version is re-read and sent again, never forced, at most three times — still refused after the third, the adoption stops as not done, as in step 4. 4) **Check it finished:** the same queries again must return no decided card without `logEntry`, in that same sense, other than the ones the owner chose to record, and no open or upcoming card without `order`. **If they do not — a batch failed, a version kept changing, a query came back short — the adoption stops here:** nothing is published, no `.ae-control-center` is written and nothing is processed; it is reported as not done, with how many cards are still unmarked or without `order`, and the next opening offers the adoption again. Say how many were marked, and how many orders were added. 5) Publish as in (a), adding `url: "<that link>"`. The database survives the republish.
     - **Then, on either path** (on (b), only once step 4 came back clean and step 5 published), in this order. **First write `meta/project`** with `name` (the repo folder's name, unless the owner gave another), `lang` (the normalized answer) and `pageSchema`, the marker of the template just published — the output of `grep -oE "const PAGE_SCHEMA = '[^']+'" ae-kit-templates/control-center.html | cut -d"'" -f2`, or `"none"` if it prints nothing ("The page's marker" in `ae-kit-templates/control-center.md`). `meta/project` is where the page takes its language from, and the marker is what lets the guide's section 2 write `recorded`. Write it with `ArtifactData` `get` on it, then `update` pinned with that version, so any other field already there stays — or `set` when the doc does not exist; a refused version is re-read and sent again, never forced. That is the only load: nothing else from the repo is written into the page. **Only once that write succeeded, write `.ae-control-center`** with `url`, `lang` and `name`, the same values. It is a file in the project: the session's next commit carries it — `open-session` never commits it. **If the `meta/project` write fails, `.ae-control-center` is not written:** it is reported as not done, with why and with the page's link, and the next opening offers the control center again — the owner can then adopt that same page with (b) instead of creating another. Writing the file anyway would leave a page in English with no marker, which no later opening would fix. **On (b), once both writes succeeded, run the guide's one-time migration** ("The one-time migration to `recorded`" in `ae-kit-templates/control-center.md`): it moves the cards marked `legacy-pre-kit` in step 3, and any already recorded, from `decided` to `recorded`. Marking them before the publish does not change: it is what lets an adoption cut short leave the page as it was. A migration that stops part way does not undo the adoption — the cards left keep `logEntry`, which section 2 already skips — and is reported with how many are left. Then run the common case's watch and query on that file, as if it had been there at the opening. Its line adds which path ran (and how many old decisions were marked, and how many the migration moved to `recorded`), whether `meta/project` was written and with which marker — if not, that `.ae-control-center` was not written either — and that a new `.ae-control-center` is left uncommitted.
6. **Recommend exactly one next action**, in this priority order:
   - If anything is `waiting on owner` — surface it first and stop there, **and lead with its `waiting_on:` question rather than the task's title**.
   - Else if anything is `in progress` — recommend resuming it, and say specifically where it left off: cite the open entries of its task log, plus the last session log — not a vague "keep going". **If `logs/tasks/<id>.md` exists**, first run `scripts/generate-task-log-view.mjs` (the view is only as fresh as its last generation), then read the view `logs/tasks/current/<id>.md`, not the whole task log: it is a summary by event type — decisions in force, findings by round with their status, the approved case groups — and it names how many notes it left behind, so when it is not enough you know to open the task log itself. **Only when there is no `logs/tasks/<id>.md`** is the task one started before its project had task logs; read the notes in its task file instead. **A task that has both** — history written in its file before the task log existed, under `## Notes` or any other heading, and a task log since — keeps that early history only in the file: read its last part, then the view.
   - Else if `TASKS.md` is empty but `BACKLOG.md` has entries — recommend the single item worth promoting next via `scope`, and say why that one: check `STATUS.md`'s "Next session" first (the project owner's own steer from last time takes precedence over guessing), and only fall back to judgment (highest apparent impact, or what unblocks something else) if `STATUS.md` doesn't already point at one.
   - Else (both empty) — say so plainly and ask the project owner what to prioritize. Never invent a task just to look useful.
7. **Keep the whole thing short.** One paragraph of state, the flags from steps 2 and 5 (if any — omit the section entirely if none), the control center's line from step 5b, and the one recommended action with its reasoning. Do not re-summarize every file that was read.

## Output
A short opening brief — current state, any staleness flags, the control center's line, and one concrete recommended next action — read before any new `scope`/`build` work starts this session.

```yaml
output:
  - kind: chat
    must_contain: current state, any staleness flags, the control center's line (watched; created or adopted; declined; or none registered with the one question offering it), and exactly one recommended next action
```
