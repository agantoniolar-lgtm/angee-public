# Kit 0.38.0

## Before installing

- List the tasks in progress and, in each, the units not integrated yet that already have work or depend on work: a unit committed but not integrated (its branch `ai/<task>-U<n>` has commits the tracked branch lacks, or its worktree is still there), and a pending unit whose `depends on:` names a unit checked off with no `commit:` line under it, which is how a unit integrated with the previous kit looks. With this version `integrate-unit.mjs` refuses both: a commit made with the previous kit has no `Task:` and `Unit:` lines and its review has no `unit:`, `commit:` and `blocking:` fields, and the dependency gate refuses a unit whose dependency has no `commit:` recorded, telling you to finish the task with the kit it started with. If the list is empty, go on. Otherwise show it to the owner and ask whether to finish that work before installing or to install anyway. Finishing first: each unit is integrated and its task closes through `ship` with the current kit, building, committing and pushing only as the owner approves, and then the install goes ahead. Installing anyway: those units can no longer be integrated through `integrate-unit.mjs`, and the owner decides how the work lands (by hand outside the script, or re-scoped as a new task). Worse, a unit committed with the previous kit has no `touches:`, and while it is in flight (its branch has work or its worktree is live) it stops the whole project, not just its task: `task-units.mjs --plan` and `integrate-unit.mjs check`, `rebase`, `integrate` and `record` of every other task exit 2 (`--plan` prints "Could not check what other tasks have, so nothing is dispatched: <task> U<n> is in flight with no valid touches:, …", and the other four print "Could not <command>: nobody can say which files other tasks have: <task> U<n> is in flight with no valid touches:, …"), and nothing is dispatched or integrated until that unit has a `touches:` or is discarded. There are two ways out, both asked of the owner first: run `scope` on that unit's task so it writes the unit's `touches:`, or discard the unit with `integrate-unit.mjs discard <task> U<n>`, which removes its worktree and branch after keeping its commit not yet integrated, and what its worktree had uncommitted, on a backup branch `ai/<task>-U<n>-backup-<k>` (files git ignores are in no backup). Do not write a `touches:` into another task outside its `scope`, even though the script's message says "fill it in". After `scope` the project moves again, but that unit is still in flight and still cannot be integrated through the script (its commit lacks `Task:` and `Unit:`), so it keeps its files away from other tasks' units until it is discarded or its task goes `done` or `dropped`. Landing it by hand, with a squash or a cherry-pick, does not release it: its branch stays ahead of the tracked branch. The owner chooses knowing this.
- **Only a project whose `.claude/skills/code-review/SKILL.md` carries a local edit that caps the review rounds per unit, declared or not (a note in the skill itself, a line in `.ae-kit-customized`, a pending or a row of "Local kit adjustments" does not exempt it):** do this before the next step. This version's `code-review` ships that cap as its default rule. Compare the project's edit with `.claude/skills/code-review/SKILL.md` as published in 0.38.0. `angee-private` keeps every version as a commit titled `kit <version>`, so read the file at that commit, not at the latest: `REF=$(gh api --paginate 'repos/agantoniolar-lgtm/angee-private/commits' --jq '.[] | select(.commit.message | split("\n")[0] == "kit 0.38.0") | .sha' | grep -E '^[0-9a-f]{40}$' | head -1)`, then, only if `$REF` is not empty, `gh api -H 'Accept: application/vnd.github.raw' "repos/agantoniolar-lgtm/angee-private/contents/.claude/skills/code-review/SKILL.md?ref=$REF"`. An empty `$REF` means nothing was read: stop and tell the owner. In the next step, convert only what differs; if nothing differs, leave the file out of the conversion, open no issue for it, and let the install replace it.
- Turn every kit file the project edited into a local adjustment, **before** installing: this installer overwrites every kit file that differs from the new version, without asking, and the edit survives only in git history. The guide arrives with this same install, so read it from `angee-private` first: `gh api -H 'Accept: application/vnd.github.raw' repos/agantoniolar-lgtm/angee-private/contents/templates/local-adjustments.md > "${TMPDIR:-/tmp}/local-adjustments.md"`, and follow its steps 1 to 6. It adds a "## Local kit adjustments" section to `CLAUDE.md` (copy the heading, its paragraph and the empty table from `templates/CLAUDE.md.template` in `angee-private`), one row per fix, opens an issue in ae-setup for each, and puts each kit file back to its installed version. It edits `CLAUDE.md`, commits and opens issues: ask the owner before starting, and before each commit and each issue.
- **Only a project with a `.ae-kit-customized` file:** every file listed in it is overwritten like any other kit file, since nothing reads that list any more. Convert each one in the previous step, with the guide; its step 6 removes the line, and deletes the list once it names no file.
- Check that no kit file the installer would change has uncommitted changes, is untracked, or is marked skip-worktree or assume-unchanged: the installer refuses with exit 4, writing nothing, when one does. Show the owner each such file and ask what to do with it: commit it, stash it (`git stash push --include-untracked -- <paths>`, which also keeps an untracked file), or wait. A change that belongs to another session or to a builder's worktree is not the session's to commit or stash: ask the owner whose it is first.

## After installing

- Commit what the install wrote, `.ae-kit-manifest` included, after showing the owner the report and with their permission: the footprint is what `check-local-adjustments.mjs` compares every kit file against. If the report lists files under "EDITED IN THE PROJECT", an edit was still in them: recover it as step 7 of `ae-kit-templates/local-adjustments.md` says, and tell the owner.
- Run `node scripts/check-local-adjustments.mjs` until it exits 0, before the next step: the hook that step adds judges its own commit. Exit 1 names what is wrong and how to fix it; exit 3 means there is no footprint, so the install did not finish. A fix that edits `CLAUDE.md` or a kit file, or that commits, is asked of the owner first.
- Add rule R38 to the rules table in `CLAUDE.md`, copied from `ae-kit-templates/CLAUDE.md.template`, and add `node scripts/check-local-adjustments.mjs || [ $? -eq 3 ]` to the pre-commit hook, in the same commit: without the hook line, `check-rule-triggers.mjs` exits 1 on that row. If the project skipped the conversion because it edited no kit file, also add the "## Local kit adjustments" section with its empty table now. Both files belong to the owner: ask before editing them and before committing.
- Add the commit-msg hook that checks every commit names its task: `.githooks/commit-msg` (or `.husky/commit-msg`, whichever the project uses) with the line `ae-kit-templates/SETUP_CHECKLIST.md.template` gives for `scripts/check-commit-task.mjs`. From now on every commit ends with a `Task: <id>` line (or `Task: none`), and a unit's commit also with `Unit: U<n>`; the kit's skills write both. Adding a hook needs the owner's permission.
- If a row of "Local kit adjustments" caps `code-review` at three rounds per unit, the kit now ships that rule: delete the row and its local files, with the owner's permission.
- If the project wants to delegate, its `CLAUDE.md` needs the delegation bullet of "Git conventions" in English, word for word from `ae-kit-templates/CLAUDE.md.template` (kit 0.37.2 brought it): it is configuration that `apply-branch-policy.mjs` recognises only verbatim, not prose. If the project carries it translated, replace the translated bullet with the English one instead of adding a second. Then run `node scripts/apply-branch-policy.mjs delegate`: it adds `.claude/worktrees/` to `.gitignore` and checks that `CLAUDE.md` carries the line, and exit 3 means it does not carry it verbatim. It edits `CLAUDE.md` and `.gitignore`: ask the owner first.
- **Only a project whose `CLAUDE.md` has no delegation bullet, in any language:** ask the owner whether the project delegates; if so, do the previous step.
- **Only a project whose `CLAUDE.md` carries the delegation bullet translated into another language:** ask the owner whether to replace it with the English one, as the step before the previous one says.
- If the project delegates, stop copying `logs/subagents/` out of a builder's worktree by hand: the subagent collector now writes to the main checkout.
- Tell the owner how units of different tasks share files now; nothing to edit. A file that another task has is waited for, never rebuilt. Another task has a file when a unit of it is dispatched and not integrated (it has a live worktree, or its branch `ai/<task>-U<n>` has commits the tracked branch lacks) and declared, wrote or has uncommitted that file, or when the branch `ai/<task>` of a task that is neither `done` nor `dropped` wrote it or its worktree has it uncommitted. `task-units.mjs --plan` lists a unit that needs such a file as waiting and names who has it, and `integrate-unit.mjs check` refuses a unit that wrote it anyway (`held`): it waits until the other lets go, then goes through `integrate-unit.mjs rebase`, which checks again and says whether it has to be rebuilt. Between two units there is one exception: the one that declared the file in `touches:` wins over one that wrote it without declaring it, and the other is refused; when both declared it, or neither did, the script does not choose and the owner decides which waits. Against a task's branch `ai/<task>` there is no exception. A unit lets go of its files when it is integrated; a task's branch, when it is integrated or its task goes `done` or `dropped`. A single-writer project runs `--plan` before each unit too, and integrates with `integrate-unit.mjs record`, which makes the same check. A unit whose builder died keeps its files with no deadline until `integrate-unit.mjs discard <task> U<n>` releases it, keeping its commit and what its worktree had uncommitted on a backup branch `ai/<task>-U<n>-backup-<k>`; running `discard` on another task's work is asked of the owner first.
- Before building the next unit of any task in progress, run `node scripts/task-units.mjs <task> --plan` on it. Tasks scoped with an earlier kit have units with no `touches:`, and exit 3 is a stop for each unit it names, not a warning: that unit is not built or dispatched, and goes back to `scope`, which writes its `touches:` for the owner to approve; the task's other units go on. A task written before units existed (checkboxes with no `**U<n>**`) builds nothing until `scope` writes its units, each with its `touches:`. Exit 2 that names another task's unit "is in flight with no valid touches:" (in `--plan` and in `integrate-unit.mjs` alike) stops every task, as "Before installing" explains: that unit's task goes back to `scope`, or the unit is discarded with `integrate-unit.mjs discard <task> U<n>`, both with the owner's permission, and nobody writes its `touches:` outside that task's `scope`.
- **Only a project whose `STATUS.md` holds a decision that cites `kit-reconciliation.md` or `.ae-kit-customized`:** this version no longer ships `ae-kit-templates/kit-reconciliation.md`, and the installer no longer reads `.ae-kit-customized`. Propose to the owner retiring that decision, together with the reconciliation process it set up (installing with `--force`, the `.ae-kit-reconcile/` folder). Local kit adjustments replace it. Editing `STATUS.md` needs the owner's permission.
